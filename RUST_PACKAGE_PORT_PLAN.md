# Rust package core and CLI port

**Status:** In progress. The Kotlin CLI remains the production CLI reference, and the Kotlin validator still supplies Android's typed content models. The Rust package crate/CLI and Android JNI reader are implemented and building, but full compatibility, host distribution, device verification, and cutover gates remain open.

## Progress record — 19 November 2026

- Step 1 is partially complete. A Kotlin-produced `.axp` archive, `validate` JSON output, `inspect` output, and build report are frozen under `crates/axiora-package/tests/fixtures/kotlin-reference/`. Nine invalid-content diagnostics are also captured and compared exactly by the Rust test corpus. The baselines were produced with the committed Gradle installation; a fresh Gradle invocation could not start in the current environment because Gradle could not determine a usable wildcard IP.
- Steps 2–3 have an initial implementation in `crates/axiora-package`: schema-0.1 directory validation, strict duplicate-key JSON parsing, stored ZIP inspection/loading, deterministic Rust archive writing, external build reports, and `validate`, `pack`, and `inspect` CLI commands. The baseline content, Kotlin archive, Rust archive, and nine selected validator cases pass current compatibility checks. This does not yet cover the complete Kotlin rejection suite or every diagnostic edge case.
- The Kotlin baseline exposes a report-field discrepancy: `inspect` reports 11,353 decompressed archive bytes, while `pack`'s build report records 13,710 bytes from raw source payload lengths plus the rewritten manifest length. Preserve both current outputs during migration unless the owner separately changes the CLI contract.
- A Rust-written archive has the same manifest digest as the Kotlin baseline and opens in the Kotlin reader, but its whole-archive digest differs because the ZIP encodings differ. The storage identity check uses the manifest digest for same-ID/version conflicts. Archive byte-for-byte writer parity is not established or required by that current identity rule.
- Step 4 has an initial Android implementation. `PackageArchiveAccess` is injected into the installer and SQLite store; Android uses a Rust JNI reader for archive inspection/loading, per-operation cache staging, and unique incoming files. The app worker serializes these calls off the main thread. The Rust loader returns validated files into a Kotlin-owned staging directory, where Kotlin currently runs `ContentValidator` again to produce the existing typed learning models. This is transitional duplicate validation, not final removal of Kotlin validation.
- The existing Android packaging flow builds and packages the Rust shared library for x86, x86_64, and arm64-v8a. `./android-app/build.sh` passed with the local SDK/NDK and Rust toolchain. JVM `content-validation` and `storage` tests passed; the Kotlin reader also opened the Rust-written archive fixture. `cargo test --workspace --offline` passed (26 passed, one font-dependent Texlet test ignored). Device verification is unavailable in this environment: ADB cannot start its local daemon because socket creation is blocked.
- Remaining gates include the complete Kotlin/Rust rejection corpus and diagnostic parity, audit and resolution of non-Android production JVM callers, clean-host CLI artifacts/target declaration, Android device import/upgrade verification (including existing learner history), and cutover. The Kotlin CLI remains production; storage callers outside Android have not been moved to a native host adapter.

## Outcome and scope

Ship a standalone `axiora` CLI that runs on supported hosts without an installed JVM. Use the same Rust package reader and validator in the CLI and Android so both agree on which `.axp` packages are valid. Port directory validation, package creation, archive inspection and loading, and the package diagnostics those operations return.

Keep the Android UI, study engine, lesson models used by Kotlin callers, learner database, and backup and installation orchestration in Kotlin. The initial compatibility target is the shipped content schema 0.1.0 and the existing `.axp` ZIP format. The proposed course descriptor in the content contract is a future schema change and is not part of this port; implement that separately with its own compatibility gate. The port itself requires no package format change, content revision bump, or learner-state migration. Installed packages, saved attempts, and notes must remain usable across the app upgrade.

This plan revisits the package tooling portion of [ADR-004](docs/markdown/decisions.md#adr-004--kotlin-domain-native-android-jvm-cli). Use the [content contract](docs/markdown/content.md), [compiler contract](docs/markdown/compiler.md), [learner-state contract](docs/markdown/learner-state.md), and [Phase 1 and 2 gates](IMPLEMENTATION_PLAN.md#phase-1--make-the-content-contract-executable) as acceptance criteria. Course review and outstanding Android release checks remain tracked in the [implementation record](IMPLEMENTATION_STATUS.md).

## Boundaries

| Component | Responsibility |
| --- | --- |
| Rust package library | Validate source directories, write archives and reports, inspect archives, and load validated revisions. Use typed results for diagnostics, descriptors, and unit data. Keep the core independent of Android, JNI, and CLI concerns. |
| Rust CLI | Parse the existing flags, map results to the existing exit codes and output formats, and handle user-supplied host paths. |
| Android Kotlin adapter | Open document picker URIs with `ContentResolver`, copy input with the archive size limit enforced into an app-private file, and pass its path and a private scratch directory to JNI. Keep SQLite, durable installation, and document-provider operations in Kotlin. |
| JNI bridge | Translate errors and validated results into Kotlin-facing representations. Contain Rust panics and prevent borrowed native memory or temporary paths from outliving their owner. |
| JVM storage callers | Depend on an injected package-reader interface for installation, reconciliation, and stored-revision verification. Android supplies the JNI-backed implementation. Identify any non-Android production JVM caller before cutover; if one exists, provide and verify a host native-library adapter for its declared targets. Test-only callers may use the Kotlin reference during migration. Do not assume that Android JNI automatically provides a usable JVM host adapter. |

Prefer the existing Android cache-file approach for the first cut. Give each operation its own file or staging directory, close handles and clean up on success or failure, and handle interrupted imports without exposing partial installs. Keep the path-based reader usable for installed archives in app-private storage. Define the JNI result ownership explicitly: either return owned validated data, or use an opaque native handle whose lifetime is closed deterministically. Do not return a staging path after Rust has deleted it. Keep preview parsing and content-model construction in Kotlin unless the port explicitly includes those models; the native reader should return the validated fields and payload bytes Kotlin needs. Audit `StudyWorkspace`, `PackageInstaller`, and `SqliteLearnerStore` before choosing the bridge shape. The current workspace serializes package operations and uses a fixed `incoming.axp`; replace that with per-operation staging before allowing concurrent work.

## Implementation sequence

1. **Capture the Kotlin baseline.** Inventory callers, CLI options and exit codes, text and JSON diagnostic fields and ordering, package identity and hashes, and writer behavior including overwrite and build reports. Freeze representative Kotlin-produced archives and diagnostic results from the illustrative course and existing invalid-input tests. Include the current `PackageInstaller` identity checks and `StudyWorkspace` preview/load paths, and determine whether any JVM-only production caller remains. Record any disagreement between the implementation and the handbook before choosing expected behavior.
2. **Port validation and archive I/O.** Add a package library in the existing Cargo workspace. Preserve strict JSON and UTF-8 parsing, duplicate-key detection, version and capability checks, graph and reference checks, and package limits. Enforce actual bytes read as well as declared sizes. Preserve ZIP entry validation, path and collision rules, hash checks, and symlink handling. If extraction is retained, constrain writes to private staging. Preserve deterministic JSON and ZIP output, report semantics, and same-directory temporary output with atomic publication and safe overwrite handling. Decide and document whether Rust exposes payload bytes or temporary staged paths to callers; the public API must make cleanup and ownership unambiguous.
3. **Port the CLI.** Implement `validate`, `pack`, and `inspect` against the library. Compare results with the baseline for success and failure. Declare the first supported host targets, build artifacts for each, and smoke-test them on clean hosts without Java. Verify path handling, including spaces and non-ASCII filenames, on each supported host.
4. **Integrate with Android and JVM callers.** Reuse the Texlet Android native build and ABI packaging approach where applicable. Add the JNI adapter and inject the reader interface into installation and stored-revision verification. Run package I/O off the Android main thread. Keep the Kotlin reader available during verification and exercise both paths against the same fixtures. If a production JVM host adapter is required, build and test it separately for declared host targets; otherwise keep the Kotlin reference confined to migration and tests and ensure no production caller depends on it after cutover.
5. **Cut over after verification.** Make Rust the default for the CLI and Android package operations once the gates below pass. Remove the Kotlin validator and archive implementation after auditing all callers, including JVM storage. Retain the compatibility corpus. Record the revised architecture decision, final build and usage commands, supported targets, and verified coverage in the handbook and implementation status. Regenerate the handbook after canonical Markdown changes.

## Acceptance gates

- **Format and identity.** Rust reads existing Kotlin archives, and the Kotlin reference reads Rust archives. Descriptors, unit revisions, and payload hashes agree. Repeated Rust builds from unchanged inputs are byte-identical. Compare whole-archive bytes with the Kotlin baseline because the exact archive bytes are retained in immutable installation and may be referenced by archive digests in future callers. Different ZIP bytes with identical manifest and payload semantics are not by themselves a package identity conflict under the current learner contract; verify the implemented same-ID/version rule (manifest hash) and preserve the ability to reopen every already-installed archive byte-for-byte. Do not require cross-writer archive equality unless the baseline proves it is part of a persisted contract.
- **Diagnostics and CLI.** Existing flags, exit codes, output formats, and diagnostic identifiers work for the baseline corpus. Reports stay outside the archive. Failed writes leave no partial destination, and the non-overwrite path cannot replace an existing file.
- **Malformed input.** Run the existing Phase 1 and 2 rejection corpus through both implementations. Cover malformed JSON and ZIP metadata, traversal, duplicate and colliding names, symlinks, undeclared payloads, size and decompression limits, and corrupt hashes. Failed validation leaves installed content and learner records intact and clears temporary files.
- **Android and storage.** Build and exercise the APK for the shipped x86, x86_64, and arm64-v8a ABIs. Verify the API 26 minimum and a representative ARM64 device. Exercise offline document picker import, preview, install, reload after process death, invalid import, and installed archive verification. Upgrade a Kotlin-backed test installation with learner history and confirm that installed revisions, attempts, and notes remain usable. Run JVM storage tests against the new reader adapter.
- **Distribution.** Each declared host artifact runs `validate → pack → inspect` on a machine without Java. Record the verified operating systems and architectures, installation instructions, and artifact checksums. Public release remains a separate decision.

## Explicit cutover prerequisites

- Freeze the compatibility corpus and expected diagnostic ordering before changing either implementation. Keep expected results as checked-in fixtures so later changes can be reviewed independently of the Kotlin reference.
- Define the reader interface in Kotlin before JNI work. It must cover inspection, validated loading for preview, and bounded archive copying/identity verification needed by install and reconciliation; the Kotlin installer must continue to own promotion, database registration, and crash recovery.
- Confirm the Android ABI list from the actual APK build configuration at implementation time. The acceptance gate's x86, x86_64, and arm64-v8a list is a proposed target set until those ABIs are confirmed as shipped.
- Treat the proposed future content schema and course descriptor as a separate compatibility milestone. A Rust reader must reject unsupported schema versions with a stable diagnostic rather than partially interpreting them.

## Cutover and recovery

Keep the Kotlin path available until the cross-reader, clean-host, and device gates pass. If a candidate fails, retain the current CLI and Android package implementation while fixing the discrepancy. During rollout, preserve the previous app and CLI build artifacts and test that the previous reader can open packages created by the candidate CLI. Keep package installation and learner storage compatible with the previous app build so recovery does not depend on rewriting archives or rolling back learner data.
